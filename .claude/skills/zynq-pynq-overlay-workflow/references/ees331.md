## Camera overlay hot-reload: proven load sequence

A camera/VDMA overlay loaded while Linux runs needs more than a successful bitstream download. v1.3 proved that BIT download plus fpga_manager `operating` can still fail first-frame recovery (`FIRST_FRAME_TIMEOUT`, both slots static, seen=[false,false]) and be misread as "cannot load online". The proven sequence (PL Reloader v1.4, 2/2 board acceptance) is:

1. Stop the original ees331-camera service safely: require an active camera.py owner, then journal evidence of VDMA_HALTED followed by BUFFER_FREED; otherwise abort and restart the original service instead of reconfiguring.
2. Build `Overlay(bit, download=False)`, validate the HWH hardware contract and VDMA parameters (C_NUM_FSTORES 3, C_INCLUDE_SG 0, 24-bit MM2S/S2MM, genlock 3/2) from ip_dict before downloading.
3. `download()`, then require `/sys/class/fpga_manager/fpga0/state` == `operating`.
4. Wait an explicit ~10 s sensor settle before touching VDMA: hot reload loses the bare-metal implicit SCCB/sensor settling. This is a timed diagnostic gate, not proof that SCCB/PCLK/VSYNC are healthy.
5. Configure VDMA/CMA, then gate READY on a ~30 s first-frame window with ~1 s progress reports of both buffer slots; success requires real frame transitions, never service `active`, download completion, or file-sync markers.
6. On FIRST_FRAME_TIMEOUT/FAIL/DEGRADED: fail closed — halt VDMA, free buffers, auto-restore the original service, and require physical HDMI/UDP confirmation for restoration.

For the fixed action payload use 8_tools/EES331_PL_Reloader_v1.4 (source 3_host/pynq/pl_reloader) rather than re-deriving this sequence. Constants in payload camera.py: SENSOR_SETTLE_SECONDS 10.0, FIRST_FRAME_TIMEOUT_SECONDS 30.0, FIRST_FRAME_PROGRESS_SECONDS 1.0.

Evidence in 4_metrics/logs: 2026-09-13_pl_reloader_v13_board_failure_audit_run01 (download PASS + first frame FAIL), 2026-09-13_pl_reloader_v14_board_acceptance_run01 and run02 (A→C success, run02 after confirmed power cycle).

## PS-only overlay baseline and proven stable reload flow (7x verified 2026-09-18)

A minimal PS7-only overlay (project `2_fpga/3_yolo_zynq/proj/yolo_zynq_test`, BD `display_test`) is the verified clean PL baseline. It was hot-reloaded **seven consecutive times without power cycling** — 5 cycles via `overlay_reload_gate.py` (run02) plus 2 full skill-literal rounds with fresh artifact directories per round (run03) — every reload gated on download return + `operating` + fresh dmesg lock, followed by ping/TCP/UDP/UART function probes, all PASS. User independently confirmed UART and Ethernet host-tool loopback on the final state. Evidence: `4_metrics/logs/2026-09-18_yolo_zynq_test_ps_overlay_run01` (first load + helpers), `..._run02_reload5x`, `..._run03_skillflow`.

Proven per-reload procedure (this IS the stable flow; scripts live on the board under `~/overlay_test/` and `~/overlay_skill_round_*/`):

1. Preflight: boot ID, service states (`ees331-camera` expected failed-terminal), `fpga0/state`, getty alive.
2. Fresh independent directory per round; upload bit + same-basename HWH pair; sha256 both sides must match byte-for-byte.
3. Ownership: camera service failed + no `/dev/dri` client = vacuous; record and proceed.
4. Load as **root** via `/usr/local/share/pynq-venv/bin/python3` with `XILINX_XRT=/usr`: `Overlay(bit, download=False)` → verify HWH contract (`ip_dict == ['processing_system7_0']` for the minimal design) → `.download()`.
5. Gate the reload on all three: `download()` returned, `fpga0/state == operating`, **dmesg `zocl … 'locked, ref=1'` count incremented by exactly 1** (each download logs a fresh UUID, so the count is a per-reload download proof; `operating` alone never proves a load).
6. Function probes per the design contract (PS-only: ping, TCP+UDP echo :7777, `/dev/console` marker).
7. Repeat back-to-back without power cycling; no cross-cycle degradation observed in 7 consecutive reloads.

Load mechanics proven on this image (PYNQ 3.0.1): `Overlay.download()` configures PL clocks **before** downloading the bitstream, so a failure at `Clocks.set_pl_clk` (`OSError: Root permissions required` when not root) means **nothing was loaded**. Run the load as root (sudo takes its password on stdin); `/dev/console` milestone writes also require root. PS-only HWH parses fine. The PS7 configuration rides the bitstream into SLCR at load: UART1 MIO 48/49, ENET0 MIO 16-27 + MDIO 52-53 + reset MIO 47, IO PLL x30 (1000 MHz, boot-matching), FCLK0 disabled is the verified-safe PS-only set; effective clocks must match the running system before loading any new PS7 config.

Loopback helpers for host-side UART/Ethernet verification live on the board at `~/overlay_test/` (`net_echo.py` TCP+UDP echo on :7777; `uart_echo.py` raw 1:1 echo on `/dev/ttyPS0`, which requires stopping `serial-getty@ttyPS0` first — that silences the COM6 console until restarted). Stop `uart_echo.py` by PID: a SIGTERM kill skips its `finally` termios restore, so prefer Ctrl-C at its console or a signal handler that restores the port; never use `pkill -f <script>.py` from a remote shell — it matches the shell's own command line and kills it mid-chain. A nohup launch chain can hang the ssh client while the service actually started; verify with a separate `pgrep`/port check instead of trusting the launch command's exit.

## Independent AXLT ABI

Project: E:/competition/2_fpga/2_axi_lite_test; BD AXI_LITE_test; CSR 0x43C00000/4KiB, read from HWH rather than hard-code in reusable drivers. IP_ID 0x41584C54, ABI 0x00010000, CAPS 1 (register-only). Command produces bitwise complement; nonzero increasing sequence, DONE held until ACK. BRAM is not implemented.

Compile mmio_ordered.c on ARM with `cc -std=c11 -O2 -Wall -Wextra -Werror -fPIC -shared mmio_ordered.c -o libmmio_ordered.so`. It uses device-MMIO volatile accesses and DSB barriers while PYNQ owns the mapping. Use the delivered hardware_contract.py before downloading.

## PC-side (Windows) automation pitfalls — all verified 2026-09-18

Driving the board from Windows PowerShell over ssh has three quoting
traps that each cost a failed round before being identified:

1. **PowerShell double-quoted remote commands evaluate `$(...)`
   locally.** `'... $(systemctl ...) ...'` must be single-quoted as a
   whole so the subexpression reaches remote bash.
2. **PowerShell -> ssh native argument passing strips embedded double
   quotes.** `sudo -S sh -c "VAR=x cmd"`, `python3 -c "..."`, and any
   remote command containing `"` break with baffling bash syntax
   errors (`unexpected EOF while looking for matching '"'`). Rules:
   single-quote the entire remote command; keep it free of ALL inner
   quotes (use `env VAR=x cmd` instead of `sh -c "VAR=x cmd"`); upload
   anything nontrivial as a FILE and execute it — never inline
   `python3 -c` one-liners through ssh from Windows.
3. **PowerShell piping a string to ssh stdin appends `\r`, so
   `'<pw>' | ssh host 'sudo -S cmd'` fails sudo authentication.** Feed
   the sudo password on the REMOTE side (`echo <pw> | sudo -S ...`) or
   use a here-file; the SSH login password uses the askpass env
   pattern (SSH_ASKPASS + SSH_ASKPASS_REQUIRE=force + DISPLAY set,
   password only in the per-call subprocess environment).

## PYNQ 3.0.1 HWH contract keys

For a module-reference IP in `Overlay.ip_dict`:
- base address key is **`phys_addr`** (int), NOT `phys` — a `.get('phys')`
  returns None and falsely fails the contract gate (cost one round).
- aperture size key is `addr_range`; `parameters` carries
  `C_BASEADDR`/`C_HIGHADDR` (hex strings) and `PROTOCOL: AXI4LITE`.
- The interface's `FREQ_HZ` parameter reflects the actual PS7 FCLK the
  BD propagated (this project's preset: 50 MHz even with
  PCW_FCLK0_PERIPHERAL_FREQMHZ absent/dynamic in the BD Tcl) — the
  bitstream's timing closed at that frequency; do not assume 100 MHz.

## Concrete failure and proven correction

2026-09-13 run01 lost communication during the first full test. The recovered event file had a valid PREFLIGHT record plus NUL/truncated data, no result.json; the host's buffered logging lost partial stdout. Do not infer an exact failure instruction from that incomplete record.

Inspection found proc_sys_reset `C_AUX_RESET_HIGH=0` with aux_reset_in tied 0. Download-only subsequently succeeded with network alive. An official generated IP simulation simultaneously proved the faulty wiring holds reset and the corrected tie 1 releases reset and permits two CSR identity reads. Corrected BIT/HWH passed 1000 register commands and 3 reloads; after service restoration UDP yielded 60 complete changing frames with zero CRC/loss/header errors. Physical HDMI is separately recorded in the run's acceptance report.

The corrected release uses const_one for auxiliary reset and dcm_locked, const_zero for debug reset. Both external and auxiliary resets are active-low. Beware Vivado HWH constants may be hexadecimal (`0x1`); compare numeric values, not literal spelling.
