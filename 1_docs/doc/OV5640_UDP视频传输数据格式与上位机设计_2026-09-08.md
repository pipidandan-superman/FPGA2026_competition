## 1. 先回答三个数字问题

| 问题 | 答案 | 计算 |
|---|---|---|
| 一帧图像多少字节？ | **921,600 B（900 KiB）** | 640 × 480 × 3（RGB888 打包，与 DDR 帧槽一致） |
| UDP 单包最大有效载荷？ | **1,472 B** | MTU 1500 − IP 头 20 − UDP 头 8 |

## 3. 方案选型：为什么用"自定义 UDP 帧头"而不是其他

| 方案 | 结论 | 理由 |
|---|---|---|
| IP 分片（直接发 >1472 B 大包） | **否决** | 任一分片丢失即整包报废；部分路由器/网卡丢弃分片；接收端无重装配控制权 |
| TCP | **否决** | 队头阻塞，一次丢包卡整流；实时视频允许丢帧不允许停流 |
| RTP/RTSP + VLC/ffplay | 备选，暂不采用 | 标准互通好，但裸 RGB 无标准 payload type，播放器支持差；引入 RTCP 复杂度不值。若日后要对标标准工具再补 RTP 封装 |
| **自定义 UDP 帧头（选定）** | ✅ | 点对点专线场景事实标准：Zynq 红外图像、水果识别等公开案例均为"lwIP RAW + 自定义帧头（魔数+帧号+包号+长度+CRC）+ C++/Python 上位机组包"；头部开销 2.2%，收发端完全可控 |

参考来源：[1] [CSDN：ZYNQ 千兆 UDP 实测 943.7 Mbps](https://blog.csdn.net/desk3/article/details/154324940)；[2] [红外期刊：基于 ZYNQ 的以太网红外图像采集与传输系统](https://hwjs.nvir.cn/cn/article/pdf/preview/762a3e31-2d37-4591-a506-dbfdacb108b1.pdf)（帧头+帧位置标志组包）；[3] [ZYNQ 实时水果识别系统](https://pdf.hanspub.org/pm20230200000_68298823.pdf)（千兆自定义 UDP 协议至上位机）；[4] [Tecphos EEVideo 规范](https://www.tecphos.com/products/eevideo-specification/)（SOF/EOF 包模式）；[5] [ADI：GMSL 桥接以太网](https://www.analog.com/en/resources/technical-articles/bridging-gmsl-and-ethernet.html)（一行一包的 MTU 对齐思路）；[6] [Xilinx Wiki：Zynq-7000 Ethernet 基准测试](https://xilinx-wiki.atlassian.net/wiki/spaces/A/pages/18842073/)；[7] [知乎：RTP 协议](https://zhuanlan.zhihu.com/p/352932897)。

## 4. 包格式（沿用实施计划 §5.2 的 32 B 头，细化标志位）

网络字节序；`UDP payload = header(32) + pixels(≤1440)`。

| Offset | 字段 | 长度 | 取值/说明 |
|---:|---|---:|---|
| 0 | magic | 4 | `0x4F 0x56 0x35 0x36`（ASCII `OV56`），接收端第一道过滤 |
| 4 | version | 1 | 0x01 |
| 5 | type | 1 | 0x01=RGB888 行数据；0x02=测试图案；0x10=JPEG（预留）；0xF0=控制/心跳 |
| 6 | flags | 2 | bit0=SOF（packet_id==0 时置位），bit1=EOF（末包置位），bit2=相机有效（0=测试图案），bit3=快照序列异常；其余保留 0 |
| 8 | frame_id | 4 | 单调递增，回绕按 32 位取模比较 |
| 12 | packet_id | 2 | 0..639 |
| 14 | packet_count | 2 | 恒 640（width=640 时） |
| 16 | payload_length | 2 | 末包 1440，本设计恒满包 |
| 18 | width / height / stride | 2+2+2 | 640 / 480 / 1920 |
| 24 | timestamp_us | 4 | 该帧快照的采集完成时刻（GlobalTimer 计数换算） |
| 28 | frame_crc32 | 4 | 整帧 921,600 B 的 CRC32（发送端对 DDR 快照一次算好，逐包重复携带） |

**关于"帧尾"的结论：不设独立帧尾包。** 完整性由三件事保证：① `packet_count` + 收齐 640 个不重复 `packet_id`；② 末包 EOF 标志 + `frame_id` 连续性；③ `frame_crc32` 整帧校验。这等价于帧尾的所有功能，还省一个包类型。上位机收到缺包/CRC 错/尺寸不符 → **整帧丢弃**（禁止补零凑数显示）。

**丢包策略（实时视频通行做法）**：跳帧不重传——显示端永远显示"最新完整帧"，统计丢失率；可选增强（阶段 C 再做）：帧间隙内 NACK 请求补发 1 轮（局域网 RTT <1 ms，15 FPS 帧间隙 66 ms 足够一轮补包）。

## 5. 发送端设计（Zynq PS，lwIP RAW）

1. **快照机制**：S2MM 正在循环写 3 个帧槽；发送时锁定"最近完成槽"（读 PARKPTR current_write 推导上一槽），发送期间该槽不被覆盖风险由 3 槽轮转吸收（发送 640 包 @ 线速约 8 ms，帧周期 ≥66 ms，安全裕量 8 倍）。
2. **零拷贝路径**：lwIP RAW `udp_sendto` + 预分配 `PBUF_POOL`；或 `pbuf_alloc_reference` 直接把 pbuf payload 指到 DDR 快照的偏移处，避免 memcpy（921 KB/帧的内存搬运是第一性能杀手）。头部 32 B 单独小 pbuf 用 `pbuf_chain` 挂链。
3. **速率整形**：640 包必须分片发送而非一次 while 烧完——按帧率配速（15 FPS：每帧 66 ms 内均匀发 640 包 ≈ 每 100 µs 一包），防止瞬间打满 64 个 TX 描述符造成 lwIP TX 阻塞饿死 RX。
4. **CRC32 成本**：软件表驱动 CRC32 约 100–200 MB/s，921 KB ≈ 5–9 ms/帧（15 FPS 预算 66 ms 的 8–14%），可接受；后续优化选项：CRC 增量计算（快照生成期间后台算）或评估 GEM TX 校验和卸载后去掉逐帧 CRC。
5. **共存纪律**：`eth_service_ms()` 轮询结构沿用 V3.1；发送循环每包之间必须回 `xemacif_input()`，保 ARP/ICMP 存活（直连链路上 PC 的 ARP 表 30 分钟过期，ARP 断了流就断——裸机流媒体最常见的坑）。
6. **基准测试先行**：先用官方 `lwip_udp_perf_server` 模板 + iperf 实测本板 RAW UDP 吞吐（预期 >500 Mbps），达标才进入视频发送（对应实施计划 H1 门限）。

## 6. 自定义上位机（必须有，结论：Python + NumPy + OpenCV）

**结论：需要。** 自定义协议 VLC/ffplay/iperf 都不认识；Wireshark 只能看不能组帧。上位机定位是"调试仪器 + 演示界面"双角色（演示阶段再升级 PyQt 界面）。

### 6.1 最小可用版 `udp_video_rx.py`（阶段 B 交付）

```text
绑定 UDP 0.0.0.0:5000，SO_RCVBUF ≥ 4 MiB
读包 → 校验 magic/version/长度 → 按 frame_id 进入装配槽
装配槽（环形 2~3 个）：bitmap 记录收到的 packet_id
EOF 且 bitmap 满 → CRC32 校验 → np.frombuffer(dtype=uint8).reshape(480,640,3)
cv2.imshow 显示最新完整帧 + 叠加信息（FPS / 丢帧率 / 乱序数）
控制台周期打印统计；Ctrl+C 退出
```

- 丢帧口径：`frame_id` 连续性缺口计数；乱序口径：`packet_id` 到达顺序逆序次数。
- 显示策略：仅显示最新完整帧；不完整帧一律丢弃并计数（与发送端语义对齐）。
- 依赖：`python -m pip install numpy opencv-python`（PC 侧已具备 Python 环境）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| RAW API 发送吞吐不足 300 Mbps | pbuf reference 零拷贝、调 `MEM_SIZE/PBUF_POOL_SIZE`、TX 描述符数加大；仍不足则降 10 FPS 或启动 JPEG（阶段 E） |
| 快照与 S2MM 写竞争 | 3 槽轮转 + PARKPTR 选"上一完成槽"；发送前校验该槽帧计缓存有效性 |
| 发送饿死接收（ARP 超时断流） | 每包间服务 `xemacif_input()`；PC 端 arp -s 绑定静态 ARP 兜底 |
| CRC32 占 CPU | 增量/后台计算；或阶段 C2 评估去掉逐帧 CRC 改采样校验 |
| 帧率与 DDR 带宽竞争（VDMA + ETH DMA） | C1 用 `HDMI_HEARTBEAT` 帧计数确认 VDMA 无错；异常先降帧率 |

## 10. 字节序勘误（v1.1，2026-09-08 板级实测后补充）

**结论：type=0x01 相机帧载荷的每像素字节序是 `[B,G,R]`，不是 v1.0 §1 隐含假设的 `[R,G,B]`。**

### 10.1 根因链路（板级证据闭环）

1. OV5640 寄存器 `0x4300=0x61`（RGB565 sequence 1）与 `cam_cap_data.v` 组字节一致，**配置无错**；HDMI 链路 `BOARD_VISUAL_PASS`（2026-09-07 冻结）进一步证明 RGB565→RGB888 的通道映射正确，`AXIS tdata[23:0] = {R[7:0], G[7:0], B[7:0]}`。
2. VDMA S2MM（AXIS 24 bit → AXI 64 bit）按 AXI 小端惯例将流字从最低字节逐个填入内存：一个 24 位像素字 `{R,G,B}` 落地为 3 个连续内存字节 `B, G, R`。
3. `udp_video_tx.c` 与快照 memcpy 均逐字节搬运，UDP 载荷忠实再现 DDR 字节序。
4. 上位机 v1.1 及此前版本按 `[R,G,B]` 解码相机帧 → 红蓝互换（黄→淡蓝、蓝紫→脏橙、淡紫→粉）。
5. **对照证据**：type=0x02 合成彩条由软件直接按 `[R,G,B]` 组包、不经 VDMA，B1 板测中显示正确（红列显示为红）⇒ 传输/解码链路字节忠实，互换仅发生在"VDMA 打包 → 解码假设"这一层。

### 10.2 修复决定（不改板端）

- **禁止**通过改 OV5640 `0x4300` 输出顺序来"纠正"：S2MM 打包与 MM2S 解包对称，HDMI 当前颜色正确，改寄存器会使 HDMI 红蓝互换，且违反冻结边界。
- **不**在 PS 端交换字节：每帧新增 921 KB 内存流量，直接吃掉 C2 提速余量（D-Cache 关闭下 CPU 内存流量是当前瓶颈）。
- **采用**：接收端按 type 感知字节序——type=0x01 按 `[B,G,R]` 解码（Pillow raw `"BGR"`；OpenCV 天然 BGR 无需变换），type=0x02 及后续软件打包类型保持 `[R,G,B]`。已实施于 `udp_video_gui.py` V1.2 与 `udp_video_rx.py` V1.1，exe 已重打包。
- 附带收益：相机载荷字节序与 OpenCV 原生 BGR 一致，后续 3_host/model 视觉模型取帧零转换开销。
- HDMI 预期不变：本修复不改变板端任何行为，HDMI 维持已验证的正确颜色；修复后 UDP 显示与 HDMI 色相一致，残余亮度/饱和度差异来自 HDMI 侧 BT.601 limited-range 转换，属预期。
