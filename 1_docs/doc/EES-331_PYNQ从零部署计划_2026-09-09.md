## 1. 可行性判定

PYNQ 官方支持的 Zynq-7000 板（PYNQ-Z1/Z2）与 EES-331 使用**同一颗芯片**，PS 侧外设布局也高度同构。逐项对比：

| 项目 | PYNQ-Z2 | EES-331 | 影响 |
|---|---|---|---|
| SoC | XC7Z020-1 CLG400 | XC7Z020-1 CLG484 | 无影响（PS 完全相同，仅封装/PL 管脚不同） |
| DDR3 | 512MB（2×MT41K128M16） | **1GB（2×MT41K256M16 RE-15E）** | FSBL 的 DDR 初始化参数与设备树 memory 节点必须改 |
| 以太网 PHY | Realtek RTL8211E-VL（RGMII, ENET0 MIO16~27） | **Marvell 88E1518**（RGMII, ENET0 MIO16~27，MDIO MIO52/53） | 设备树 PHY 节点必须改；接线拓扑相同 |
| 控制台串口 | UART1 MIO48/49，ttyPS0 | UART1 MIO48/49，USB3.0 座 | 无影响，直接兼容 |
| 启动介质 | microSD（SD0） | microSD（SD0），SW8 = 0,0,1,1,0,x | 无影响 |
| USB | USB2.0 OTG | USB2.0 OTG（JP6/JP7 跳帽需设为 Host） | 小改（跳帽） |
| PL 外设（HDMI 等） | ADV7511 等，配套 base overlay | ADV7511 + OV5640 + 数码管等，走自己的 base overlay | base overlay 必须自做（本来就要做） |

**结论**：所有差异都落在"FSBL + 设备树 + base overlay"三处，全部是标准适配工作，不需要改内核、不需要改 PYNQ 上层软件。风险集中在 DDR 与 PHY 两点，均有明确验证手段（见第 7 节风险表）。

## 2. 路线选择

| 路线 | 内容 | 优点 | 代价 | 定位 |
|---|---|---|---|---|
| **A. 适配官方预编译镜像（推荐先行）** | 下载 PYNQ-Z2 v3.0.1 镜像 → 用自建 EES-331 FSBL 重打 BOOT.BIN → 修改设备树（memory 1GB、PHY 88E1518）→ 烧卡启动 | 最快出结果；rootfs/内核/Jupyter 全部现成；风险隔离在启动链早期，串口日志可观测 | 不算严格意义的"全部自建"；后续升级镜像需重复适配 | 第一阶段必做 |
| **B. PYNQ sdbuild 全量自建** | 在 Ubuntu 22.04 主机克隆 PYNQ 仓库 v3.0.1，建 `boards/EES-331` BSP，跑 sdbuild 生成专属镜像 | 完全可控、可复现、可提交（赛题要求工程可复现）；板名/外设名全部正确 | 需 Linux 主机 + Vitis/PetaLinux 2022.2 + 约 100GB 磁盘 + 首次构建数小时；环境问题多 | 路线 A 跑通后按需执行 |
| C. 任意 Linux + `pip install pynq` | 在自建 PetaLinux/Debian 上装 pynq Python 包 | 最小系统 | 无官方支持路径，Jupyter/驱动/rootfs 全自己兜底，踩坑无社区先例 | 仅作了解，不采用 |

**为什么 A 先行**：A 的所有适配产物（EES-331 PS 配置、FSBL、设备树补丁）100% 复用于 B 的 BSP；先在 A 上把硬件问题（DDR/PHY）排掉，B 只是工程化封装。

## 3. 分阶段执行计划

> 执行边界（项目策略）：`2_fpga/` 为冻结基线。以下凡涉及新建工程/目录的动作，启动前需用户明确授权；建议新建 `2_fpga/2_pynq_port/`（Vivado 硬件工程 + BSP 材料），所有构建、烧卡、串口证据进 `4_metrics/logs/YYYY-MM-DD_<task>_runNN`。每阶段结束按 daily-engineering-log 落日志。

### 阶段 0：资源与前置确认（0.5 天）

- 确认资源：≥8GB microSD 卡 1 张、读卡器、USB 双公头线（或板载 USB 串口直接用 USB3.0 座）、网线 + 能跑 DHCP 的路由器/直连 PC、Linux 环境（实体机/虚拟机/WSL2 均可，WSL2 需支持 loop 挂载与 `dtc`/`mkimage`）。
- 工具清单：**Vivado/Vitis 2025.2（现装版本，v1.1 修订）**——冻结基线经核实即为 2025.2（见第 0 节证据表），路线 A 的 XSA/FSBL/bit 直接用现装 2025.2 产出，无需另装 2022.2；2022.2 仅路线 B sdbuild 官方构建流程需要，届时单独安装；`dtc`、`mkimage`/`dumpimage`（u-boot-tools）、balenaEtcher、bootgen（随 Vitis）。
- 下载并校验：PYNQ-Z2 v3.0.1 官方镜像，直链 `https://www.xilinx.com/bin/public/openDownload?filename=pynq_z2_v3.0.1.zip`（pynq.io 页面的 bit.ly 短链国内可能不可达），下载后记录 SHA-256；备选 v3.1.1：`https://download.amd.com/opendownload/pynq/pynq_z2_v3.1.1.zip`（适配步骤与 v3.0.1 相同，若采用则文中 2022.2 相关引用顺延为其对应工具代）；PYNQ 仓库 v3.0.1 源码（`sdbuild/prebuilt` 填充说明与 u-boot 来源，见阶段 2 步骤 4；u-boot 首选可直接从官方镜像 BOOT 分区提取，仓库克隆可延后）。
- **PASS 判据**：镜像与工具就位清单写入当日日志；镜像 SHA-256 记录入 run 目录。

### 阶段 1：EES-331 PYNQ 硬件平台（XSA）制作（1 天）

1. 新建 Vivado 工程（器件 xc7z020clg484-1），例化 PS7，按下表配置（DDR 与时钟抄冻结工程实测值，外设按手册）：

| PS 项 | 配置 | 依据 |
|---|---|---|
| DDR | MT41K256M16 RE-15E ×2，32bit，533.333MHz，1GiB，外部 Vref，训练全开 | 冻结工程 PS7 实测（Zynq_PS7_Config_Report 第 5 节；该报告源自 2020.2 旧导出，落地时以当前 2025.2 工程 `ps7_init.tcl` 复核为准） |
| 时钟 | 晶振 33.333333MHz；FCLK0 = 100MHz 输出 PL | 冻结工程同款 |
| UART1 | MIO48/49，115200（控制台） | 与冻结工程、手册一致 |
| SD0 | 使能（引脚按手册第 9 节图形化配置），用于启动 | 手册第 9 节 |
| ENET0 | RGMII，MIO16~27，MDIO MIO52/53；PHY 型号 88E1518 | 手册第 13 节 |
| USB0 | 使能（MIO28~39），板上 JP6/JP7 跳帽设 Host | 手册第 7 节（USB 小节） |
| QSPI | 暂不使能（SD 启动不需要；如后续要固化再开） | — |

2. PL 侧先放**最小 base overlay**：PS7 + 一段 AXI GPIO/或直接引出 EMIO GPIO 点板载 LED（验证 Overlay 加载即可，比赛功能后迁）。生成 bit、导出 XSA（含 .hwh）。
3. 用 XSA 在 Vitis 2025.2 里生成 **EES-331 专用 FSBL**（Release），同时导出 `ps7_init.tcl` 备查。
- **PASS 判据**：XSA、bit、fsbl.elf 三个文件落 run 目录并记 SHA-256；JTAG 模式下用 fsbl+bit 能在串口看到 FSBL 横幅、`ps7_init` 后 DDR 1GB 可写读（Vitis 内存测试或 xsct `mrd/mwr` 抽查 0x08000000 与 0x30000000）。

### 阶段 2：路线 A——适配 PYNQ-Z2 v3.0.1 镜像（1~2 天，核心阶段）

1. **烧原镜像做基线观察（可选但强烈建议）**：先把未修改的 PYNQ-Z2 镜像烧卡、SW8 拨 0,0,1,1,0,x 启动，UART1 115200 记录完整启动日志。预期两种结果：能进系统但内存只认 512MB（Z2 的 FSBL 按其 DDR 初始化）或停在 DDR 训练。无论哪种，都拿到 u-boot 环境变量、boot 分区文件清单（`BOOT.BIN / boot.scr / image.ub` 或 `uImage / devicetree.dtb`，以实际为准）这份关键情报。
2. **拆 FIT / 提取设备树**：若 dtb 打包在 `image.ub`，用 `dumpimage -T flat_dt -p N -o system.dtb image.ub` 提取；否则直接取 `devicetree.dtb`。`dtc -I dtb -O dts` 反编译。
3. **两处设备树修改**：
   - `memory` 节点：`reg = <0x0 0x40000000>`（1GB）；
   - PHY：把 realtek 节点换成 88E1518（内核 `CONFIG_MARVELL_PHY` 驱动按 PHY-ID 自动绑定，通常无需 compatible；`reg` 填原理图 PHY 地址，若未知先用 `phytool`/`mdio` 扫描确认）。改完 `dtc` 编回 dtb；若原镜像是 FIT 结构则 `mkimage` 重打包 `image.ub`。
4. **重打 BOOT.BIN**：bif = EES-331 fsbl.elf + base.bit + u-boot（来源优先级：PYNQ v3.0.1 sdbuild prebuilt 包内现成 u-boot → 从官方 BOOT.BIN 提取 → 按 PYNQ 仓库 tag 自编译；每次来源与哈希记入 run 目录）。`bootgen` 生成新 `BOOT.BIN`，连同改好的 `image.ub`/dtb 写回 SD 卡 BOOT 分区。
5. **首次正式启动**：上电，串口全量抓日志（fsbl 横幅 → u-boot → kernel → systemd），插网线看 `eth0` DHCP，PC 浏览器开 `http://<板IP>:9090` Jupyter（默认 xilinx/xilinx）。
- **PASS 判据**：串口日志 + Jupyter 截图 + `free -h` 显示 ≥900MB + `ethtool eth0` 显示 1000Mb/s 且 ping 通网关。全部证据入 run 目录。**未达 PASS 不进入下一阶段。**

### 阶段 3：Overlay 与 Python API 验证（0.5~1 天）

1. 把阶段 1 的 bit+hwh 拷到板上 `/home/xilinx/pynq/overlays/ees331_base/`，Jupyter 中 `Overlay("ees331_base.bit")` 加载，验证 `overlay.ip_dict`、`register_map` 读 GPIO/AXI IP 寄存器。
2. AXI DMA loopback（`pynq.allocate` + `sendchannel.recvchannel`）验证 HP 口数据通路——这是后续 OV5640 视频链路 Python 化的前提。
3. 88E1518 吞吐实测：iperf3 板↔PC。
- **PASS 判据**：三个 notebook（加载/寄存器、DMA loopback、iperf）输出截图与 .ipynb 存 run 目录。

### 阶段 4：比赛功能迁移（与现有进度并行，2~4 天）

1. 把冻结工程已验证的 VDMA+OV5640+ADV7511 链路重新打包进 base overlay（Vivado 里重新连 PS（ENET/SD0/USB 已是新配置）+ 原 PL 模块，仅改 PS 不动 PL 逻辑）。
2. Python 侧接管：OV5640 寄存器配置走 PL IIC 或 PS IIC 的 MMIO 封装、VDMA 用 `pynq.lib.video` 或寄存器级封装、ADV7511 初始化封装成类。
3. 与 AI PC 的 UDP 视频流（`OV5640_UDP视频传输数据格式与上位机设计_2026-09-08.md` 的协议）在 PYNQ 侧用 Python socket 重写发送端。
4. 产出**通用 PYNQ Skill**（赛题加分项方向）：Overlay 加载与校验流程、DMA 封装、88E1518 网络自检脚本——按赛题要求写明"换板卡/换题目仍可用"。
- **PASS 判据**：HDMI 出图 + Jupyter 内单帧抓图 + 上位机收到 UDP 流，三证据齐。

### 阶段 5（可选）：路线 B——sdbuild 全量自建镜像（3~7 天）

前置：Ubuntu 22.04 主机（原生或虚拟机；WSL2 可行但 loop 挂载/权限问题多，预留排错时间）、Vitis 2022.2 + PetaLinux 2022.2（sdbuild 对工具版本敏感，现装 2025.2 不能替代，需按 v3.0.1 官方要求单独安装）、≥100GB 磁盘。

1. `git clone -b v3.0.1 https://github.com/Xilinx/PYNQ.git`；按官方说明手工填充 `sdbuild/prebuilt/`（rootfs 等，v3.0.1 起默认为空必须先填）。
2. 建 `boards/EES-331/`：`EES-331.spec`（BOARD=name、(bitstream)、根文件系统默认）+ `base/base.bit` + `base/base.hwh` + 阶段 1 的 XSA/BSP。
3. `make BOARDDIR=boards/EES-331`，产物 `EES-331-3.0.1.img` 烧卡复测（PASS 判据同阶段 2）。
4. 价值：镜像可提交、可复现，符合赛题"工程水平/他人能复现"的考察点。
- **回退**：任何一步失败直接回到路线 A 成果，不影响比赛主线。

## 5. 必改项清单（差异驱动，防遗漏）

- [ ] FSBL：必须用 EES-331 的 1GB DDR 配置重新生成（不可沿用镜像内 Z2 FSBL）
- [ ] 设备树 `memory` = 0x40000000（1GB）
- [ ] 设备树 PHY：realtek → marvell 88E1518（确认 MDIO 地址）
- [ ] BOOT.BIN 重打包（fsbl + bit + u-boot）
- [ ] SW8 启动拨码 = SD 启动（0,0,1,1,0,x，注意 ON=0 的定义方向）
- [ ] JP6/JP7 跳帽：USB 置 Host
- [ ] base overlay 自建（PYNQ-Z2 的 base.bit 管脚约束不适用于 CLG484 板）
- [ ] 内核 `CONFIG_MARVELL_PHY` 可用性确认（PYNQ 内核大概率已含，用 `zcat /proc/config.gz | grep MARVELL_PHY` 验证；缺失则配模块编译）

## 6. 风险登记表

| 风险 | 概率 | 影响 | 缓解/验证 |
|---|---|---|---|
| DDR 初始化不匹配导致启动挂死/内存不稳 | 中 | 高 | 阶段 1 先 JTAG 下用 EES-331 FSBL 验证 DDR 全 1GB 可写；阶段 2 串口日志定位挂在 DDR 训练还是 u-boot |
| 88E1518 内核驱动缺失或 MDIO 地址不对 | 低 | 中 | `phytool` 扫总线；驱动缺失则模块编译；最坏 100M 也能跑（不影响 Jupyter） |
| FIT 重打包（image.ub）出错 | 中 | 中 | 先 `dumpimage -l` 记录原始结构再原样回包；失败则改 u-boot 从 tftp/分离 dtb 加载做中间验证 |
| u-boot 获取困难 | 低 | 中 | 三级来源（prebuilt/提取/自编译）见阶段 2 步骤 4 |
| WSL2 挂载/权限问题 | 中 | 低 | 虚拟机或实体机兜底；SD 卡操作也可在 Windows 用 Etcher + DiskGenius/ext4 工具替代 |
| 工具链差异引入 ps7_init 差异 | 极低（v1.1 降级） | 低 | 已核实冻结基线即 Vivado 2025.2（`.xpr` + XSA 元数据，见第 0 节），FSBL 与 ps7_init 用同装 2025.2 生成，无跨代差异；剩余唯一搭配点：镜像内 2022.2 产的 u-boot/内核与 2025.2 FSBL 同 BOOT.BIN，属常规组合，阶段 2 首启串口日志即可验证 |
| 时间挤占比赛主线（Vitis C 链路已跑通） | 中 | 高 | 本计划独立于现有主线推进；任何阶段超时 1 天即暂停评估，回到"PC Python + Vitis C"主线（2026-09-01 既定决策） |
