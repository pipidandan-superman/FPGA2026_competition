## 2. 已确认的基线

### 2.1 板卡与 PS 网口

| 项目 | 已确认值 |
|---|---|
| 板卡 | EES-331 |
| SoC | `xc7z020clg484-1`，Zynq-7020 |
| PS DDR | 1 GiB DDR3 |
| 网口控制器 | Zynq PS `ENET0/GEM0` |
| PHY | Marvell 88E1518 |
| RGMII | MIO16-MIO27 |

| MIO Bank0 | 3.3 V |
| MIO Bank1 | 1.8 V |

以太网 MIO 与现有 UART1 不冲突。网口位于 PS 侧，不需要在 PL XDC 中添加 RGMII 管脚约束。

### 2.2 当前工程状态

当前 `display_test.bd` 和 `display_test_wrapper.xsa` 中：

```text
PCW_ENET0_PERIPHERAL_ENABLE = 0
PCW_EN_ENET0               = 0
PCW_ENET0_GRP_MDIO_ENABLE  = 0
```

因此当前 XSA/Vitis 平台不能直接使用板载网口。后续必须先在 Zynq Processing System 中启用 GEM0 和 MDIO，再生成新的硬件平台。

### 2.3 当前视频数据路径

```text
OV5640 DVP
  -> PL RGB565采集
  -> RGB888扩展
  -> Video In to AXI4-Stream
  -> AXI VDMA S2MM
  -> PS DDR三帧缓存
  -> AXI VDMA MM2S
  -> HDMI监督显示
```

当前 Vitis 应用使用：

| 项目 | 数值 |
|---|---:|
| 分辨率 | 640 x 480 |
| 内存格式 | 24-bit packed RGB888，实际字节顺序待测试图确认 |
| 每行步长 | 1,920 bytes |
| 每帧有效数据 | 921,600 bytes，`0x000E1000` |
| 帧缓存数量 | 3 |
| 单槽大小 | 1 MiB，`0x00100000` |
| Frame 0 | `0x10000000` |
| Frame 1 | `0x10100000` |
| Frame 2 | `0x10200000` |

DDR 中究竟是 `RGB`、`BGR` 或其他字节顺序，不能仅根据 24-bit 总线声明决定，必须通过固定彩条和 PC 原始字节验证后冻结。

## 3. 赛题对应关系

### 3.1 FPGA/Zynq 的实际作用

FPGA/Zynq 不能只作为普通 USB、串口或 GPIO 转接板。当前设计中 FPGA/Zynq 已承担：

- OV5640 DVP 实时采集。
- RGB565 到 RGB888 的硬件流水转换。
- AXI4-Stream 视频组织。
- VDMA 与 DDR 三帧缓存。
- HDMI 独立监督显示。
- 后续可加入图像预处理、ROI 或特征提取。

因此，以太网应负责把 FPGA 产生的实时数据送往 AI PC，而不是取代上述硬件作用。

### 3.2 AI PC 与 FPGA/Zynq 协同

最终系统需要说明并实测：

- 上行视频、ROI、特征或状态数据流。
- 下行控制命令和参数流。
- 时间戳或时钟同步方法。
- RTT、有效吞吐率、丢包率和错误率。
- 指令超时、断网恢复和安全状态。
- FPGA 硬件处理对延迟、吞吐率或确定性的实际贡献。

10G Ethernet 是鼓励项和 KR260 参考场景，不是 EES-331 原型必须达到的门槛。禁止用理论 1 Gbit/s 链路速率代替实测应用层吞吐率。

### 3.3 AI PC 证据边界

- 普通 PC 可以用于早期 GEM0、UDP、Wireshark 和 OpenCV 调通。
- 普通 PC 测试必须标为原型或协议调试证据。
- 正式赛题结果应在 AMD Ryzen AI PC 上复测，并记录具体型号、操作系统、驱动和软件版本。

## 4. 推荐总体架构

```text
OV5640
  -> PL采集、格式转换
  -> VDMA S2MM
  -> DDR三帧循环缓存
  -> PS判断已完成帧
  -> DCache Invalidate
  -> 独立发送快照缓冲区
  -> lwIP220 Raw API
  -> PS GEM0
  -> 88E1518 RGMII PHY
  -> UDP视频流
  -> PC接收、重组、CRC验证
  -> OpenCV显示/保存
  -> Ryzen AI模型推理与任务规划
```

视频数据面采用 UDP。控制、状态和异常处理使用独立端口，并加入序号、CRC、ACK、超时和重试；机械臂控制协议必须在实际控制器选型后单独确定。

## 5. 网络与协议基线

### 5.1 初始网络配置

| 设备 | 配置 |
|---|---|
| EES-331 | `192.168.1.10/24` |
| PC | `192.168.1.100/24` |
| 网关 | 初期不配置 |
| 视频端口 | UDP 5000，Zynq -> PC |
| 控制/状态端口 | UDP 5001，双向，后续 Gate 启用 |
| MTU | 1500，不依赖 Jumbo Frame |

MAC 地址必须使用团队自有的本地管理地址并在文档中固定，不能让多块板卡使用同一个地址。

### 5.2 视频包格式

使用网络字节序。固定头长度 32 字节：

| Offset | 字段 | 长度 | 说明 |
|---:|---|---:|---|
| 0 | magic | 4 | 固定标识，例如 ASCII `OV56` |
| 4 | version | 1 | 协议版本 |
| 5 | type | 1 | 视频、测试数据或控制类型 |
| 6 | flags | 2 | 像素顺序、首尾包及异常标志 |
| 8 | frame_id | 4 | 单调递增帧号 |
| 12 | packet_id | 2 | 帧内包号，从 0 开始 |
| 14 | packet_count | 2 | 当前帧总包数 |
| 16 | payload_length | 2 | 当前包有效图像字节数 |
| 18 | width | 2 | 图像宽度 |
| 20 | height | 2 | 图像高度 |
| 22 | stride | 2 | DDR 每行字节数 |
| 24 | timestamp_us | 4 | PS 侧帧完成时间戳，允许回绕 |
| 28 | frame_crc32 | 4 | 完整有效帧 CRC32 |

### 5.3 分包参数

```text
应用头               = 32 bytes
单包图像载荷         = 1440 bytes
UDP payload          = 1472 bytes
IPv4 packet          = 1500 bytes
每帧有效图像         = 921600 bytes
每帧数据包           = 640 packets
```

这样可以在标准 MTU 下避免 IP 分片，并且 1,440 字节可被 3 整除，不会在 RGB888 像素内部拆分。

PC 端收到缺包、CRC 错误或尺寸不一致的帧时必须整帧丢弃，不能补零后当作有效结果。

## 6. 带宽边界

| 帧率 | 仅图像有效载荷 |
|---:|---:|
| 1 FPS | 7.373 Mbit/s |
| 5 FPS | 36.864 Mbit/s |
| 15 FPS | 110.592 Mbit/s |
| 30 FPS | 221.184 Mbit/s |
| 60 FPS | 442.368 Mbit/s |

以上尚未包含 UDP/IP/Ethernet 帧间隙和协议开销。结论：

- 百兆链路不能承载 640 x 480 RGB888 15 FPS 及以上目标。
- 30 FPS 原始视频要求实际协商为 1 Gbit/s，并且 PS/lwIP 的实测吞吐足够。
- 初始调试从单帧和 1 FPS 开始，不允许直接宣称 30 FPS。
- 若原始流无法达到目标，优先顺序为：降低帧率 -> 上传 ROI -> 上传 FPGA 预处理结果或特征 -> 最后再评估压缩。

## 7. VDMA 帧一致性策略

### 7.1 禁止直接读取正在写入的帧

VDMA S2MM 持续循环写三个 DDR 槽。如果 PS 在 VDMA 写入期间发送同一槽，会产生上下半帧来自不同时刻的撕裂。

### 7.2 推荐第一版

1. 轮询 S2MM 状态和 `PARK_PTR` 当前写帧编号。
2. 观察写帧编号发生变化，确定刚完成的槽。
3. 验证 `PARK_PTR` 编号与实际槽地址的映射，禁止直接假设。
4. 对源帧执行 `Xil_DCacheInvalidateRange()`。
5. 将 921,600 个有效字节复制到独立的 1 MiB 发送快照缓冲区。
6. 对快照计算 CRC32。
7. 从快照缓冲区分成 640 个 UDP 包发送。

快照地址候选为 `0x10300000`，但执行前必须与链接脚本、lwIP 内存池和其他预留区做完整地址冲突检查。该地址在检查通过前不得写入代码。

### 7.3 后续优化

- 第一版使用“Invalidate + Copy + lwIP pbuf”保证正确性。
- 只有在正确性、丢包统计和缓冲区生命周期全部验证后，才考虑 zero-copy。
- 如果轮询产生漏帧或时序不确定，再评估把 VDMA S2MM 中断连接到 PS `IRQ_F2P`；该操作属于额外 BD 变更，必须独立审批。

## 9. PC 抓取操作路径

### 9.1 Wireshark 预验证

1. 选择连接 EES-331 的有线网卡。
2. 关闭该网卡不相关的虚拟网桥或共享功能。
3. 设置静态 IP。
4. 使用捕获或显示过滤器：

```text
udp.dstport == 5000
ip.src == 192.168.1.10 && udp.dstport == 5000
```

5. 首先确认源/目的 MAC、IP、UDP 长度和包号递增。
6. 保存 `.pcapng` 到对应 `4_metrics/logs/<run-name>`。

### 9.2 Python/OpenCV 接收

实现顺序：

1. 只接收并计数。
2. 解析 32-byte 头。
3. 按 `frame_id/packet_id` 重组。
4. 保存 `.raw`。
5. 校验 CRC32。
6. 通过已确认的字节顺序转换为 NumPy 图像。
7. 最后启用 OpenCV 显示和 AI 推理。

性能测试时应提供无显示模式，因为 `imshow()` 和磁盘保存会降低 PC 接收吞吐率。

## 10. 失败恢复与回退

| 失败位置 | 恢复措施 |
|---|---|
| H1 PS 参数误改 | 关闭工作副本，不保存；从冻结哈希重新开始 |
| H2 时序或实现失败 | 保留完整日志，停止；不得覆盖已验证 BIT/XSA |
| PHY 无法识别 | 检查 HWH、MIO、MDIO、供电、网线和 PHY 地址扫描；不接摄像头 |
| 仅协商到 100 Mbit/s | 停止 15/30 FPS 测试，检查线缆、PC 网卡、PHY 配置和自协商 |
| UDP 丢包 | 先降低包速率/帧率并扩大 PC 接收缓冲，区分发送端与 PC 端瓶颈 |
| 图像偏色 | 保存 RAW，检查 DDR 字节顺序，禁止凭显示效果直接交换通道 |
| 图像撕裂 | 检查完成帧选择、快照复制和缓冲区生命周期 |
| CRC 错误 | 停止显示该帧，保留包级证据，定位首个错误包 |
| 摄像头/HDMI 回归 | 立即回退到冻结 BIT/XSA 和原应用，网络 Gate 判失败 |

## 11. 强制停止条件

出现任一条件立即停止当前 Gate：

- 新 XSA/HWH 中仍没有 GEM0 或 MDIO。
- ENET0 配置导致 DDR、UART1、FCLK0、GP0、HP0 或 HP1 非预期变化。
- PHY 无法稳定识别。
- 未确认链路速率却进入高帧率测试。
- `PARK_PTR` 帧编号映射未验证。
- DDR 字节顺序未验证。
- 缓存维护或快照地址存在冲突。
- 丢包、CRC 错误或不完整帧被隐藏。
- 摄像头、VDMA 或 HDMI 基线出现回归。
- 原始证据没有写入规定的 `4_metrics/logs/<run-name>`。
